## What this pass found and fixed

**1. The settings screen promised something the server does not do.** It said leaving the
key box empty would keep the key already saved. The server actually *deletes* the stored
key whenever the box is empty. A person opening Settings to change only which AI they use
would have silently lost their key, and their clips would have quietly stopped being
summarised — with nothing on screen to say why.

Fixed on the screen: it now says plainly that saving with the box empty removes the key.
**The deeper fix is a server change and has not been made** — see below.

**2. "Failed to fetch".** When the server could not be reached, the app showed the
browser's own words. It now says *"you appear to be offline."*

## Still open after this pass

**The settings behaviour itself.** Telling the truth on screen is a patch, not the answer.
Leaving the key box empty should keep the key, because that is what a person expects and
because losing it costs them their summaries. That is a change to
`backend/src/worker.js:279` — only overwrite the stored key when a key was actually sent —
and it touches the part of the system that holds users' keys, so under the project's own
rule it ships with a test that proves it. Not done: it is working code, and changing it is
Jaiswal's call.

**A link that is on a supported site but is not a video.** `https://instagram.com` with
nothing after it was accepted, queued, tried three times and then failed. The failure is
visible and nothing broke, so this is untidy rather than dangerous — but it leaves a dead
entry in the notebook that the person did not ask for. Worth deciding whether the check
should require a link that actually points at a video.

**The phone.** Not tested, and not testable yet. Sign-in is only allowed from `localhost`
until the app is on a real web address, so it cannot be opened on a phone. Two things go
untested until then: how it looks on a small screen, and the Android share sheet — which
is the only way anyone is meant to capture a reel at all. **This is the largest untested
area in the product.**

**The copy-paste tier.** The screen offers "Copy and paste — no key needed", but the part
that hands the person the text to paste and takes the reply back is not built.

**One piece of test rubbish left in staging** — the `https://instagram.com` entry above.
Deleting it was blocked, and it is harmless where it is.

## Worth knowing for the next test run

The browser holds on to its copy of `app.html` hard enough that an edited file appears not
to have changed — an offline test silently ran against the old version and looked like a
failure of the app. Add something like `?v=2` to the address after editing, or the run
proves nothing.

## The gap closed: real use on a phone

The section above said the phone was the largest untested area — the small-screen layout
unseen and the Android share sheet never run, and the share sheet is the only way anyone is
meant to capture a reel (D17). **Both are now closed, and not by a test — by real use.**

Jaiswal installed the app on his phone from the staging address, signed in with a third
account, connected a Gemini key, and shared reels to it **through the Android share sheet**,
confirmed by him.

| What the database shows | |
|---|---|
| Reels captured from the phone | 5, all Facebook |
| How they arrived | the Android share sheet |
| State of every one | `analyzed`, on Gemini, shared |
| Time from written down to summarised | 1–2 seconds each |
| Intervention needed | none |

One of those five was captured before a key was connected, so it sat written-down and
unsummarised. Pressing **Summarise it now** summarised it 4 hours 44 minutes after it was
transcribed — which is both the proof that feature works and the reason it exists.

**So the whole product has now been exercised end to end by a real person on a real phone:**
share a reel → fetched → transcribed → summarised → filed → readable, searchable, and
annotatable. That was the thing this project set out to build.
